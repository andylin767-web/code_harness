## Code Review: schema.sql

### Summary
The schema defines a single `users` table for a typical user authentication system. The schema is clean and minimal but has several gaps that should be addressed before production use—lacking indexes on frequently-queried fields, cleanup lifecycle fields, and security considerations around password storage.

### Critical Issues
1. **No index on `email` lookup** (lines 3–4)
   - Problem: Although `email` is marked `UNIQUE` (which implicitly creates a unique index in PostgreSQL), login flows typically query by `email` with `password_hash` lookup. If the application also queries by `username` for login, both are covered by the UNIQUE constraint. However, if any other columns (e.g. `created_at` for sorting) or future columns are involved in queries, there are no explicit indexes.
   - Impact: Performance degradation at scale for common query patterns.
   - Fix: Verify the UNIQUE constraint on `username` and `email` is sufficient for all query paths. Add explicit indexes for any additional query patterns (e.g., `CREATE INDEX idx_users_created_at ON users(created_at);`).

2. **No `deleted_at` or soft-delete mechanism** (all lines)
   - Problem: Hard-deleting users destroys audit trails and violates referential integrity in downstream tables (sessions, orders, etc.).
   - Impact: Data loss, orphaned records in related tables, compliance issues (GDPR right-to-erasure has nuance).
   - Fix: Consider adding `deleted_at TIMESTAMP WITH TIME ZONE DEFAULT NULL` for soft deletes, or document the hard-delete strategy.

### Improvements
1. **Add `CHECK` constraints on `email` format** (line 4)
   - Description: No validation at the database level that `email` is well-formed. Application-level validation alone is insufficient if other services or scripts touch the DB.
   - Suggested Change: `CHECK (email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$')`

2. **Consider adding a `role` or `status` column** (line 2)
   - Description: Most user systems need role-based access (admin, user, etc.) or account status (active, suspended, pending verification).
   - Suggested Change: Add `role VARCHAR(20) NOT NULL DEFAULT 'user'` or `status VARCHAR(20) NOT NULL DEFAULT 'active'` with a CHECK constraint.

3. **`updated_at` auto-update not enforced** (line 7)
   - Problem: `updated_at` defaults to `NOW()` on insert but does not auto-update on row changes. PostgreSQL does not have `ON UPDATE CURRENT_TIMESTAMP` like MySQL.
   - Suggested Change: Create a trigger:
     ```sql
     CREATE OR REPLACE FUNCTION update_modified_column()
     RETURNS TRIGGER AS $$
     BEGIN
       NEW.updated_at = NOW();
       RETURN NEW;
     END;
     $$ LANGUAGE plpgsql;

     CREATE TRIGGER set_updated_at
       BEFORE UPDATE ON users
       FOR EACH ROW
       EXECUTE FUNCTION update_modified_column();
     ```

4. **Missing `login_at` tracking field** (line 6)
   - Description: No field to track last login time, useful for security monitoring and identifying dormant accounts.
   - Suggested Change: Add `last_login_at TIMESTAMP WITH TIME ZONE DEFAULT NULL`.

5. **No explicit schema/table comment** (top of file)
   - Description: Adding a comment improves discoverability in database tooling.
   - Suggested Change: `COMMENT ON TABLE users IS 'Core user accounts for authentication and identity management';`

### Positive Notes
- Clean, well-formatted DDL with aligned columns for readability
- Proper use of `TIMESTAMP WITH TIME ZONE` for temporal columns (UTC-safe)
- Sensible `VARCHAR` lengths (50 for username, 255 for email and password_hash)
- `NOT NULL` constraints applied to all required fields
- `UNIQUE` constraints on username and email prevent duplicate accounts
- Uses `SERIAL` for auto-incrementing primary key (standard PostgreSQL pattern)

[ ] Needs major revision

The schema is structurally sound for a basic users table. The critical items (auto-updating `updated_at`, soft-delete consideration) and the checkpoint on indexes should be resolved before this schema is used in a production environment.
